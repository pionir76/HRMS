# EmergencyStop 모듈

비상정지 실행/해제 모듈(2026-09-29 구현). **이 시스템에서 장비에 무언가를 쓰는 유일한 동작이다** — TLC 프로토콜이 제공하는 쓰기 기능 자체가 DO 접점 출력 하나뿐이다.

API 형식은 [api-manual.md](../../Doc/api-manual.md) 75·76번, 프로토콜 상세는 [pclink protocol.md](../../Doc/pclink%20protocol.md) 4장.

## 내부 구성

- `Controllers/EmergencyStopController.cs` — `POST /api/equipments/{id}/emergency-stop`(정지), `.../release`(해제). 권한 확인과 HTTP 응답 변환만 한다.
- `Services/EmergencyStopService.cs` — 실제 처리. 대상 압축기 선정 → 중복 실행 차단 → D1805 쓰기 → 응답 확인 → D1805 되읽기 → DB 반영 → 이력 기록.

상태 판정(폴링 쪽)은 이 모듈이 아니라 `Modules/Communication/CompressorPollingService`가 매 사이클 D1805를 읽어 `Compressor.IsEmergencyStopped`에 넣고, `EquipmentStatusAggregator`가 **1번 압축기 값**을 장비에 옮긴다.

## 사양 (확정 2026-09-29)

| 항목 | 결정 | 이유 |
|---|---|---|
| 레지스터 | **D1805 하나로 상태 조회와 쓰기를 모두 한다.** D1801은 쓰지 않는다 | 아래 "D1801을 쓰지 않는 이유" |
| 단위 | **장비 단위** | DO가 장비의 비상정지 버튼 회로에 물려 있어, 압축기 한 대에서 내보낸 DO가 장비 전체를 멈춘다 |
| 대상 압축기 | **1번 압축기만**(`SequenceNo` 최소). 쓰기도 상태 판정도 1번만 보고 2번 이후는 무시. 1번에 IP가 없으면 실패. LG도 동일 | 모든 압축기에 비상정지 회로가 있지만 시스템 단순화를 위해 통일(사용자 결정 2026-09-29). 판정도 1번만 보므로 "해제했는데 다른 압축기 때문에 안 풀리는" 경우가 생기지 않는다 |
| 권한 | 시스템관리자 / 안전관리총괄자 / 안전관리책임자 | 장비를 멈추면 운영이 중단되므로 책임자급 이상. **담당 장비 여부는 보지 않는다** — 비상 상황에서 담당이 아니라는 이유로 막으면 위험하다 |
| 해제 권한 | 정지와 동일 | 사용자 결정 |
| 통신 장애 시 | 막지 않고 시도, 실패하면 사유 반환 | 통신 상태는 최대 3초 전 정보라 지금은 살아있을 수 있다. 비상 상황에서 서버가 지레 막는 게 더 위험하다 |
| 이력 | `EventLogs`의 `EmergencyStop` 카테고리 | 전용 테이블은 두지 않는다(사용자 결정). 명령문·응답·상태확인 결과는 메시지에 담는다 |
| 중복 실행 방지 | TLC(IP)별 `SemaphoreSlim`. 처리 중이면 즉시 거부 | overview.md 4.8 요구사항. 장비가 아니라 IP를 키로 쓰는 건 LG 7개 셀이 D1805 하나를 공유하기 때문 |
| 사용자 재확인 | **정지만 비밀번호 재입력**을 서버가 검증(틀리면 400, 거부도 이력에 남김). 해제는 재확인 없음 | 프론트 요청 2026-09-29. 400을 쓰는 이유는 401이면 프론트가 로그아웃 처리하기 때문 |

### D1801을 쓰지 않는 이유

원래 사양은 "상태는 D1801(DIOSTS)의 비트 8, 명령은 D1805"였다. 샘플 TLC로 실제 명령을 보내 보니:

| 레지스터 | 쓰기 전 | `01WRD,001,1805,0001` 후 |
|---|---|---|
| D1805 | `0x0000` | **`0x0001`** |
| D1801 | `0x0000` | `0x0000` (변화 없음) |

D1801로 판정하면 **비상정지를 걸어도 3초 뒤 폴링이 "정상"으로 되돌려 놓는다.** 예전 시스템의 조회 명령(`01RRD,009,...,0099,1805`)도 D1805를 읽고 있었고 실측과 일치했다. 사용자가 사양을 "D1805가 DIO 상태 정보와 쓰기를 모두 수행한다"로 확정했다.

## 설계에서 정한 것

- **LG 배터리 #1~#7은 한 몸으로 움직인다.** 7개 셀의 1번 압축기가 TLC(`10.90.87.217`)를 공유해 D1805가 하나뿐이다. 한 셀에 비상정지를 걸면 폴링상 7개 셀이 모두 비상정지로 보인다(사용자 확인 후 확정).
- **폴링 읽기와는 직렬화하지 않는다.** TLC별 잠금은 명령끼리만 막는다. 폴링은 요청마다 새 TCP 연결을 열고 실장비 시험에서 TLC 1대에 42개 동시 접속도 견뎠다(2026-09-28). 읽기까지 이 잠금에 묶으면 LG 냉동기 42대가 순차 처리되어 폴링 주기(3초)를 못 지킨다.
- **되읽기 실패는 명령 실패가 아니다.** 쓰기 응답이 OK면 성공으로 보고, D1805 되읽기로 실제 반영까지 확인됐는지는 `confirmed`로 따로 돌려준다. 폴링이 3초 안에 다시 읽어 맞춘다.
- **되읽기는 250ms 간격으로 최대 2초까지 반복한다.** TLC는 쓰기에 OK를 먼저 돌려주고 레지스터 반영은 0.4~0.8초 뒤에 한다(2026-09-29 실측 — 400ms까지 예전 값, 800ms에 새 값). 처음 구현은 OK 직후 한 번만 읽어서 **실기기에서 매번 "미확인"**이 나왔다. 지금은 보통 0.85초 안에 확인되어 응답한다.
- **명령 결과를 DB에 즉시 반영한다.** 폴링을 기다리면 최대 3초 동안 화면이 예전 상태를 보여준다. 1번 압축기와 장비만 바꾼다(집계가 1번 값만 본다).
- **통신이 끊긴 사이클에는 상태를 갱신하지 않는다**(마지막으로 확인된 값 유지). 모르는 것을 "해제됨"으로 보이게 하는 쪽이 더 위험하다.
- **실패 응답에도 현재 상태를 담는다.** 정지된 장비의 해제가 실패했는데 화면이 "해제됨"으로 보이면 안 된다.
- **테스트 모드**(`Communication:TestMode=true`)에서는 TCP 쓰기 없이 상태만 바꾸고, 폴링도 비상정지 상태를 덮어쓰지 않는다(모의값에 8번째 자리가 없다). 그래서 TLC 없이 화면 검증이 가능하다. 단 `Communication:RealDeviceIps`에 적힌 TLC는 테스트 모드여도 실제로 쓰고 읽는다(`Modules/Communication/CommunicationMode.cs`, setup.md 19.1).

## 실기기 검증 (2026-09-29, 샘플 TLC `59.16.212.252`)

- `01RRD,001,1805` 단건 읽기, `01RRD,008,<센서7>,1805` 조회 모두 정상 응답
- API로 `01WRD,001,1805,0001` 전송 → 응답 OK, D1805가 `0x0001`로 유지됨
- 정지·해제 모두 `confirmed: true`, 응답 약 0.85초(되읽기 재시도 적용 후)
- 실모드 폴링이 D1805를 읽어 해당 장비를 `isEmergencyStopped: true`로 판정함

**실설치 때 확인할 것**: 샘플 TLC에는 냉동기가 물려 있지 않아 아래 두 가지는 아직 보지 못했다(사양상으로는 둘 다 그렇게 동작한다).

- DO 출력(`0001`)이 설비를 실제로 멈추는지
- 현장 패널의 물리 비상정지 버튼을 눌렀을 때 D1805에 반영되는지 — 폴링이 이 값을 읽어 화면에 띄우는 것이므로, 반영되지 않으면 현장 버튼으로 멈춘 장비가 화면에 "정상"으로 보인다
