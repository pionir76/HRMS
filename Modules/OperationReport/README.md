# OperationReport 모듈

운전일지 모듈. Front_Work.md 10번 화면(운전일지)에 대응한다.

`Modules/Operation`(가동률/운전상태 판정)과는 이름이 비슷하지만 완전히 다른 모듈이다 — 그쪽은 실시간 집계, 이쪽은 사용자가 결재까지 거치는 일일 문서다. 헷갈리지 않도록 이름을 다르게 뒀다.

## 구조

- 운전일지 1건 = **장비 1개 + 날짜 1개(일 단위)** — 점검일지(주 단위)와 다름
- 하루 중 정해진 4개 시각(**09:00 / 13:00 / 16:00 / 21:00**, 전 장비 공통 고정값)마다 항목별로 값을 기록
- 항목은 "구분"(냉매계통/냉수계통/전기계통/기타) 아래 16개 표시행으로 구성되고, 그중 4개(토출압력/토출가스온도/흡입압력/오일압력)는 **압축기 수만큼 행이 반복**된다 — 나머지 12개는 장비당 1행
- 결재 3단계(안전관리원/안전관리책임자/안전관리총괄자) — [Modules/Approval](../Approval/README.md) 공용 헬퍼를 점검일지와 동일하게 재사용

## 항목별 자동화 방식 — 세 갈래로 갈린다 (사양 변경 반영)

같은 "운전일지 자동화"라도 항목에 따라 동작이 다르다. 판정은 아래 **우선순위 순서대로** 적용한다.

### 우선순위 규칙 (전체 공통)

1. **장비가 운영 중이 아니면(통신 오류/미사용/폐기 등) 그 장비의 모든 항목은 무조건 `/`.** 아래 2~4번 규칙보다 우선한다 — 특히 "사용자 마지막 입력 이어받기"(4번)도 이 규칙 앞에서는 무시되고 `/`로 강제된다.
   - "운영 중이 아님"의 기준: `Equipment.Status`가 미운영/철거/사용중지 중 하나이거나, `Equipment.CommunicationStatus`가 연결됨이 아닌 경우(끊김/재접속중) — 원래 `CompressorPollingService`의 수집 제외 기준과 맞춘 것이다.
   - **불일치 주의(2026-09-17)**: 수집 기준이 "`운영` 상태만 수집"으로 바뀌었지만, 운영이 아닌 장비의 운전일지·점검일지 작성 사양은 **추후 결정**하기로 해서(사용자 2026-09-17) 이 기준은 옛 그대로 뒀다. 그래서 지금은 수리중/점검중/철거예정/기타 장비가 수집은 안 되는데 운전일지에서는 운영 중으로 판정되어, 멈춰 있는 값으로 채워질 수 있다. 사양이 정해지면 `OperationAutoFillService.NonOperationalStatuses`를 같이 고친다.
2. **운전 중이 아니면, 채널 자동측정/장비설정 랜덤값 항목은 `/`.** ("운전"의 정의는 아래 참고. 사용자 직접입력 6개 항목은 이 규칙의 대상이 아니다 — 운전 여부와 무관하게 마지막 입력을 계속 이어받는다.)
3. 위 1~2번에 해당하지 않으면, 항목 종류별로 아래 A/B/C를 따른다.

**운전의 정의**: 그 장비에 속한 압축기 중 단 하나라도 전류값(CH07)이 `Equipment.RunningCurrentThreshold`를 넘으면 운전 중이다 — 이미 계산되어 있는 `Equipment.IsRunning`을 그대로 읽어서 쓴다(`EquipmentStatusAggregator` 참고, 여기서 새로 판정하지 않는다).

### A. 채널 자동측정 (5개) — 조건을 통과하면 그 시각 채널값으로 무조건 덮어씀

| 표시 항목     | 채널                                                      | 범위               |
| ------------- | ----------------------------------------------------------- | ------------------ |
| 토출압력      | 고압 (CH05)                                               | 압축기별 (반복 행) |
| 토출가스 온도 | 고온 (CH02)                                               | 압축기별 (반복 행) |
| 흡입압력      | 저압 (CH04)                                               | 압축기별 (반복 행) |
| 오일압력      | 오일압력 (CH06)                                           | 압축기별 (반복 행) |
| 운전전류      | 운전전류 (CH07) — 항상 1번 압축기(`SequenceNo=1`) 값 사용 | 장비당 1행         |

- 압축기가 통신 불가 상태이거나 그 채널값을 읽어온 적이 없으면 `/`(기존 규칙 유지, 위 우선순위 1~2번과 별개로 압축기 단위에서 한 번 더 확인).
- 사용자가 그 시각 칸을 미리 편집해놔도, 조건을 만족하는 자동 측정 시각이 오면 채널값이 덮어쓴다. 점검일지의 자동 기록(빈 칸만 채움)과 정반대 방향이라 그 코드를 재사용하지 않는다.

### B. 장비설정 기반 랜덤값 (5개) — **사양 변경으로 신규**, 더 이상 채널을 안 읽는다

냉각수온도(입구), 냉각수온도(출구), 브라인온도(입구), 브라인온도(출구), 운전전압 — 이전엔 냉각수온도가 CH01 채널값을 그대로 읽었지만, `Equipment`에 냉각수/브라인/전압 각각의 "유무" + "정상범위(min/max, 냉각수·브라인은 입구/출구 각각)" 속성이 생기면서(`Modules/Equipment/README.md` 참고) 이제 **채널을 읽지 않고 장비 설정을 기준으로 값을 만든다.**

- 그 장비가 해당 항목을 "사용 안 함"(`Has* = false`)이면 `/`.
- "사용함"(`Has* = true`)이면, 해당 min~max 사이의 랜덤값을 만들어 **항상 소수점 1자리로 반올림/패딩해서** 저장한다 — 단순 반올림이며 raw 스케일 변환(예: 10으로 나누기) 같은 건 아니다. 예: `100` → `100.0`, `12.345` → `12.3`, `0` → `0.0`.
- min/max가 둘 다 `0`이어도(장비 스펙상 실제로 있을 수 있는 값) 유효한 범위로 취급해서 `0.0`을 기입한다 — `0`은 "값 없음"이 아니다.
- min 또는 max가 `NULL`이면(설정 자체가 안 됨) 범위를 만들 수 없으므로 `/`.
- 위 "우선순위 규칙" 1~2번(비운영/비운전)이 여기도 그대로 적용된다 — "사용함"이어도 장비가 꺼져있으면 `/`.

| 표시 항목        | 소스                                                  |
| ---------------- | ------------------------------------------------------ |
| 냉각수온도(입구) | `HasCoolingWater` + `CoolingWaterInletMin/Max`        |
| 냉각수온도(출구) | `HasCoolingWater` + `CoolingWaterOutletMin/Max`       |
| 브라인온도(입구) | `HasBrine` + `BrineInletMin/Max`                      |
| 브라인온도(출구) | `HasBrine` + `BrineOutletMin/Max`                     |
| 운전전압         | `HasVoltage` + `VoltageMin/Max` (입구/출구 구분 없음) |

### C. 사용자 직접입력 (6개) — 빈 칸일 때만 직전 값을 이어받음

냉매량, 오일량, 단자대&판넬상태, 드레인상태, 저압부단열재상태, 이상진동및소음상태 — 전부 채널/장비설정 매핑이 없어서 사람이 직접 관측/판단해야 하는 항목이다.

- 사용자가 값을 수정하면, 다음 관측 시각이 도래할 때 그 값을 그대로 이어받는다(빈 칸만 채움 — 이미 있는 값은 절대 안 덮어씀).
- 이 이어받기는 **하루 안(9→13→16→21)에서 끝나지 않고 다음 날 레포트로도 계속 이어진다** — 한 번 기록하면 사용자가 다시 수정하기 전까지 무기한 유지된다.
- **단, 위 우선순위 1번(장비 비운영)에 해당하면 이 이어받기도 무시되고 `/`로 강제 기입된다** — 이번 사양 변경으로 추가된 예외다. "운전 중이 아님"(우선순위 2번)은 이 6개 항목에는 적용되지 않는다 — 운전 여부와 무관하게 사람이 눈으로 확인하는 항목이라서다.

## 기준값 (실측 기준, 14개)

16개 표시 항목 중 냉각수온도/브라인온도는 입구·출구가 기준값 하나를 공유해서, 실측 기준 텍스트는 총 14개다: 토출압력, 토출가스온도, 흡입압력, 오일압력, 냉매량, 오일량, 냉각수온도, 브라인온도, 운전전압, 운전전류, 단자대&판넬상태, 드레인상태, 저압부단열재상태, 이상진동및소음상태.

- 장비당 자유 텍스트 1개씩(`string`, 예: `"1.8MPa 이하"`).
- **사용자가 한 번 수정하면, 그 값이 그 장비의 이후 모든 날짜 레포트에 그대로 이어진다.** 매번 최신값을 실시간으로 반영하는 게 아니라, **레포트(그 날짜)마다 값을 실제로 저장**해두고 새 레포트를 만들 때 가장 최근 레포트의 값을 그대로 복사해오는 방식이다 — 그래야 나중에 기준값을 바꿔도 이미 결재까지 끝난 과거 문서가 조용히 바뀌지 않는다(이 프로젝트 전반의 원칙 — 결재자 이름 스냅샷 저장, 이벤트 로그 메시지 미리 조립 등과 동일한 이유).

## 공통 규칙

- **운전일지는 절대 누락되면 안 된다.** 채널 자동측정 항목은 사용자 입력 없이도 채널값이라는 객관적 소스가 항상 있으므로, 장비를 등록한 순간부터 매일 자동으로 생성되어야 한다 — 점검일지의 "사용자가 최초 1회 직접 작성해야 하고 시스템은 임의 데이터를 만들지 않는다"는 정책과 **정반대**다.
- **결재 완료 후 수정 잠금은 프론트엔드가 UI로만 처리한다.** 점검일지처럼 백엔드가 PUT을 막는 방식(`409`)을 여기서는 쓰지 않는다 — 백엔드는 결재 상태와 무관하게 항상 저장 요청을 받아준다(사양 변경 가능성이 있어서 백엔드에 강하게 고정하지 않기로 함).
- **레포트 형식(구분/사용장비/항목명 등 표시 메타데이터)은 백엔드가 관리하지 않는다.** 프론트가 그 형식을 소유하고, 백엔드는 항목을 가리키는 키와 값만 저장한다. 다만 채널 자동측정 7개 항목만은 자동화 로직이 "이 키는 어느 채널을 읽어야 하는지" 알아야 하므로, 그 7개의 키↔채널 매핑만 백엔드 코드에 상수로 둔다(표시 라벨/구분은 여전히 프론트 소관) — 구현 시작 시 이 7개 키 이름을 프론트와 맞춰야 한다.

## DB 구조 (설계안 — 아직 코드/마이그레이션 없음)

테이블 3개로 구성한다. 점검일지(`InspectionLog`/`InspectionResult`)와 달리 항목이 "장비당 1개"와 "압축기별 반복"으로 섞여 있고, 기준값(14개)이 관측값(16개)과 성격이 달라서(하루 4번이 아니라 장비당 1개) 테이블을 분리한다.

### 1. `OperationLog` — 장비 1개 + 날짜 1개

```
Id                    PK
EquipmentId           FK → Equipment
Date                  DateOnly
Level1ApproverId/ApproverName/ApprovedAt   (안전관리원)
Level2ApproverId/ApproverName/ApprovedAt   (안전관리책임자)
Level3ApproverId/ApproverName/ApprovedAt   (안전관리총괄자)
CreatedAt / UpdatedAt
```

- 유니크 인덱스 `(EquipmentId, Date)` — 점검일지의 `(EquipmentId, WeekStartDate)`와 같은 원칙.
- 결재 컬럼 구조와 판정 로직은 `Modules/Approval`을 그대로 재사용한다(3단계 전부 `Required`).

### 2. `OperationItemValue` — 16개 표시 항목의 관측값 (하루 4개 시각)

```
Id            PK (surrogate)
LogId         FK → OperationLog
ItemKey       string   -- 16개 표시 항목을 가리키는 키 (레이블/구분은 프론트 소관, 백엔드는 키만 앎)
CompressorId  FK → Compressor, nullable   -- 압축기별 4개 항목(토출압력/토출가스온도/흡입압력/오일압력)만 채워짐, 나머지 12개는 null(장비 단위)
Time0900      string?
Time1300      string?
Time1600      string?
Time2100      string?
```

- 압축기별 항목과 장비 단위 항목을 한 테이블에 같이 두되 `CompressorId`로 구분한다 — 컬럼(Time0900~2100)을 두 번 정의하는 중복을 피하기 위해서다. 대신 `(LogId, ItemKey, CompressorId)` 유일성은 DB 제약이 아니라 애플리케이션 코드가 보장한다(NULL이 섞인 복합키는 Postgres에서 유일성 보장이 깔끔하지 않음 — `EventLog`가 이미 참조 컬럼에 FK/유니크 제약을 안 거는 것과 같은 이유로, 이 프로젝트에서는 이런 경우 앱 레벨 신뢰를 택해왔다).
- 값은 전부 `string`으로 저장한다 — O/X/`/`와 실측 숫자 문자열이 같은 컬럼에 섞여 들어가고, 값의 형식 자체도 백엔드가 강제하지 않기 때문이다(점검일지의 Sun~Sat 컬럼과 같은 방식).
- 채널 자동측정 5개(`토출압력/토출가스온도/흡입압력/오일압력/운전전류`)와 장비설정 기반 랜덤값 5개(`냉각수온도(입구)/(출구)/브라인온도(입구)/(출구)/운전전압`)의 `ItemKey`는 자동화 서비스가 참조해야 하므로 코드 상수로 둔다. 나머지 6개(사용자 직접입력)는 어떤 `ItemKey`가 오든 백엔드가 검증하지 않고 그대로 저장한다.

### 3. `OperationReferenceValue` — 14개 기준값 텍스트 (장비 단위, 압축기 구분 없음)

```
Id            PK
LogId         FK → OperationLog
ItemKey       string   -- 14개 기준값 키. 압축기별로 반복되는 항목(예: 토출압력)도 기준값은 압축기 구분 없이 장비당 1개
ReferenceText string?
```

- 압축기별로 반복되는 4개 항목도 기준값 자체는 압축기 구분 없이 장비당 하나다(양식 예시에서 압축기 1/2/3번 모두 같은 기준값이 반복되는 것과 일치).
- 새 `OperationLog`를 만들 때, 그 장비의 가장 최근 `OperationReferenceValue`를 그대로 복사해서 시작한다(사용자가 수정하지 않는 한 이후 날짜에도 계속 이어짐). 관측값과 마찬가지로 매번 스냅샷을 저장하므로, 나중에 기준값을 바꿔도 이미 결재된 과거 문서는 안 바뀐다.

## 내부 구성

- `Models/OperationLog.cs` — 운전일지 엔티티(장비+날짜, 결재 Level1~3 인라인)
- `Models/OperationItemValue.cs` — 16개 표시 항목의 하루 4개 시각 값(`CompressorId` nullable)
- `Models/OperationReferenceValue.cs` — 14개 기준값 텍스트
- `Models/AutoMeasuredItemCatalog.cs` — 채널 자동측정 5개 항목의 키↔채널 매핑 상수
- `Models/EquipmentRangeItemCatalog.cs` *(예정)* — 장비설정 기반 랜덤값 5개 항목의 키↔`Equipment` 속성(Has/Min/Max) 매핑 상수
- `Models/Dtos.cs` — 조회/저장 API DTO
- `Controllers/OperationLogsController.cs` — 조회/저장/결재 API (`Modules/InspectionReport/Controllers/InspectionLogsController.cs` 패턴 재사용, 단 PUT 잠금은 없음)
- `OperationAutoFillService.cs` — 매일 한국시간 09/13/16/21시, **하루 4회** 실행되는 `BackgroundService`. 채널 자동측정 5개 + 장비설정 랜덤값 5개는 위 "우선순위 규칙"에 따라 항상 덮어쓰고, 사용자 직접입력 6개·기준값은 빈 칸만 이어채운다(날짜 경계도 넘음, 단 장비 비운영 시는 예외)
