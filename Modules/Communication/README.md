# Communication 모듈

TCP 통신 모듈 + 프로토콜 모듈.

- 압축기별 TCP 연결 관리 (연결/해제/재사용)
- 전용 프로토콜 파서 (요청 패킷 생성, 응답 패킷 파싱, 비정상 패킷 검출)
- 응답 타임아웃 처리 및 자동 재접속
- 압축기별 통신 상태 관리 (연결됨/끊김/재접속중)
- 압축기 통신 장애가 다른 압축기 수집에 영향을 주지 않도록 격리

## 내부 구성

- `PcLinkClient.cs` — PC-Link 프로토콜 송수신/파싱(체크섬 검증, 16비트 2의 보수). 연결을 유지·재사용하지 않고 폴링 사이클마다 새로 연결하고 끊는다
- `CompressorPollingService.cs` — 3초 주기 폴링 백그라운드 서비스. 수집 대상은 **장비 상태가 `운영`인 장비의 압축기만**(`CollectionTargets`, 2026-09-17 사양 확정 — overview.md 4.1). 사이클이 끝까지 성공할 때마다 `LastCycleCompletedAt`을 갱신한다(`GET /api/system/status`의 수집 서비스 점검용). 채널값 갱신, 통신 상태 관리, 경보 판정(`Modules/Alarm`) 호출, 장비 단위 집계(`EquipmentStatusAggregator`) 트리거

## 압축기별 레지스터 맵과 TLC 공유 구조 (사양 확정 2026-09-18, **미구현**)

### 현장 구성

TLC는 센서 7개를 읽고 DO 출력 모듈이 붙은 장치다. 남양연구소 장비는 크게 세 종류인데, **서버가 구분해야 하는 것은 두 가지뿐이다.**

| 종류 | 구성 | 서버 입장 |
|---|---|---|
| 구형(센서 설치형) | 압축기 1대 = TLC 1대, 압축기의 7개 지점 센서를 직접 읽음 | 표준 배치(360/361/362/364/365/366/367) |
| Fric(자체 HMI 보유) | TLC가 장비의 HMI와 통신해 7개 값을 받아 같은 레지스터에 채움 | **구형과 완전히 동일** |
| LG 냉동기(B지구 환경차개발시험2동 배터리시험셀 1~7) | 물리 기기 1대 안에 장비 7대 × 압축기 6대 = 42대. **TLC는 1대**, 그 TLC가 LG 냉동기와 통신해 42대 값을 모아둔다 | IP/MAC이 42대 모두 같고, **압축기마다 읽을 주소가 다르다** |

LG 배치(셀별 30개 블록, 압축기당 4개 + 셀 공유 CH07, CH03·CH06 센서 없음)는 [Doc/pclink protocol.md](../../Doc/pclink%20protocol.md) "레지스터 주소는 압축기별 설정값이다" 절에 압축기 42대 전체 주소표로 정리해뒀다(예전 시스템 자료에서 옮겨 적은 것이며, 그 원본 파일은 제거했다).

### 현재 구현의 한계

`PcLinkClient.ReadChannelsAsync`는 읽을 주소가 상수(`ReadRegisters`)로 고정돼 있다. 그래서:

1. **LG 42대가 전부 같은 값을 받는다** — 같은 IP에 같은 요청을 42번 보내 모두 360~367을 읽는다. 셀 2~7의 실제 값은 조회되지 않는다.
2. 읽어온 상태 레지스터 값을 폴링이 그냥 버린다(`Values[0..6]`만 사용). 게다가 읽는 주소가 D1805인데 상태 판정은 **D1801**을 읽어야 한다.

### 구현 방향 — 압축기 개별 통신을 그대로 유지한다 (사용자 결정 2026-09-18)

TLC(IP) 단위로 묶어서 한 번에 읽는 방식도 검토했지만, **예외를 만들지 않는 쪽**을 택했다. LG도 다른 장비와 똑같이 **압축기 1대 = 요청 1번**으로 처리한다. 같은 IP로 여러 압축기가 동시에 접속하는 것은 허용한다.

- **읽는 값은 항상 8개**: CH01~CH07(압축기별 주소) + **D1801**(비상정지 상태). 기존의 D0099(UNUSED)는 뺀다.
- 센서가 없는 채널(LG의 CH03·CH06)은 주소가 비어 있다. 응답 인덱스가 밀리지 않게 그 자리에는 더미 주소(D0099)를 넣어 읽고 값은 버린다 — 이렇게 하면 요청 형태가 전 장비 동일하게 고정된다.
- 요청당 8개라 RRD의 64개 제한에 걸릴 일이 없다. 분할 로직이 필요 없다.
- 폴링 루프(압축기별 `Task.WhenAll`)와 값 저장 로직은 그대로 두고, 주소만 DB에서 읽어 넘긴다.

### 구현 상태 (2026-09-18 완료)

- `CompressorChannelSetting.RegisterAddress`(nullable)에 채널별 주소를 저장한다. 표준 장비는 360/361/362/364/365/366/367, LG 42대는 압축기별 주소가 들어가 있고 CH03·CH06은 `null`(센서 없음)이다.
- **`Enabled`와 `RegisterAddress`는 한 쌍이다**(사용자 결정 2026-09-18): 사용 안 함으로 저장하면 서버가 주소를 지우고, 사용으로 저장하는데 주소가 없으면 `400`으로 거절한다. 모순된 조합(사용 안 함인데 주소가 남아 값이 계속 저장되거나, 사용인데 주소가 없어 값이 안 들어오는 상태)을 아예 만들 수 없게 한 것이다. 그래서 폴링의 "주소 없으면 건너뛴다" 한 줄이 곧 "사용 안 함"과 같은 뜻이 된다. 값은 수집하되 경보만 끄려면 `AlarmEnabled`를 쓴다.
- `PcLinkClient.ReadChannelsAsync(ip, registers)`가 주소 7개를 받아 `01RRD,008,...,1801` 프레임을 만든다. `null`인 자리에는 더미 `0099`를 넣고 응답값은 버린다.
- 폴링은 사이클 시작 시 `LoadChannelRegistersAsync`로 압축기별 주소를 읽어 넘기고, 주소가 없는 채널은 값을 저장하지 않는다.
- 조회/수정 API는 기존 채널 설정 API에 필드가 추가됐다(`GET`/`PUT /api/compressors/{id}/channel-settings` — api-manual 5-1·25번). 주소를 바꾸면 다음 사이클부터 바로 적용된다.
- 8번째로 읽는 D1801 값은 아직 쓰지 않는다 — 비상정지 모듈(`Modules/EmergencyStop`)에서 사용 예정이다.

**실기기 확인(2026-09-18)**: 압축기 1대를 실제 TLC(`59.16.212.252`)로 돌려 7채널이 3초마다 갱신되는 것을 확인했고, LG 42대를 같은 TLC로 몰아 **동시 접속 42개**도 시험했다 — 사이클마다 40~41대 성공, 1~2대 실패(3~5%)로 하드 리밋은 없었다. 시험 절차와 결과는 `Doc/setup.md` 20장에 정리했다.

### 남은 작업

- **관리 화면 연동**: 압축기별 채널 설정 화면에 주소 입력란 추가(프론트 작업 필요).
- **비상정지 모듈**: D1801 판정 + D1805 쓰기. 쓰기가 폴링 읽기와 겹치지 않도록 TLC별 쓰기 큐나 잠금이 필요하다(예전 시스템도 쓰기 큐를 썼다).

### 같은 TLC에 동시 접속 42개 — 1차 확인 완료, 현장 재확인 필요

LG TLC 1대에 압축기 42대가 물려 있어 3초마다 같은 장치로 TCP 연결 42개가 동시에 열린다. 2026-09-18에 실제 TLC 1대(`59.16.212.252`)로 42개를 몰아서 시험한 결과 **사이클마다 40~41대 성공, 1~2대 실패**였다. 동시 접속 하드 리밋은 없지만 3~5%는 그 사이클 값을 놓친다. 실패가 30초 연속되지 않으면 통신 장애 경보는 뜨지 않는다.

**실제 LG TLC가 아니라 다른 TLC에 42개를 몰아넣은 시험**이므로 현장에서 재확인이 필요하다. 실패율이 더 높으면 **코드 구조를 바꾸지 않고** IP별 동시 실행 수만 제한(예: IP당 4~8개)해서 완화할 수 있다 — 읽기 경로는 그대로 하나다. 매 사이클 재연결 부담 자체도 실장비 장시간 검증 항목으로 남아 있다.

### 비상정지 (전 장비 공통)

읽기는 **D1801**, 쓰기는 **D1805**다. 판정은 `(D1801 값 & 0x0100) != 0`이고, 명령은 `01WRD,001,1805,0001`(정지) / `...,0000`(해제)다. **LG라고 해서 특수 동작은 없다**(사용자 확인 2026-09-18). 현재 폴링은 D1805를 읽고 있어 **D1801로 바꿔야 한다.**

## 통신 실패 처리 (2026-09-28 보강)

### 실패 사유를 구분한다

`PcLinkClient.ReadFailureReason`으로 원인을 나눠 돌려준다 — `연결실패`/`연결타임아웃`/`응답타임아웃`/`연결끊김`/`체크섬오류`/`오류응답`/`값개수부족`. 예전에는 모든 실패가 `Ok=false` 한 비트로 뭉개져서, 현장에서 값이 안 들어올 때 전원·케이블 문제인지 프로토콜 이상인지 구분할 수 없었다(overview.md 4.2가 요구하는 "비정상 응답 로그"도 불가능했다).

사유는 두 곳에 남는다.
- **막 끊긴 순간**(연결됨 → 실패)에 `ILogger` 경고 1줄. 매 사이클 남기면 전 압축기 장애 시 3초마다 수백 줄이 쌓이므로 전이 시점만 남긴다.
- **통신 장애 경보 이벤트 메시지**에 `(사유: 응답타임아웃)`처럼 덧붙는다.

### 잘린 응답을 성공으로 보지 않는다

응답이 `OK`이고 체크섬이 맞아도 **값이 요청한 8개보다 적으면 실패**(`값개수부족`)다. 이 검사가 없던 때는 잘린 응답이 "정상 통신"으로 처리되어 통신 상태는 `연결됨`인데 값만 멈추고, 그 옛 값으로 경보 판정이 계속됐다. 2026-09-28에 값 1개만 돌려주는 가짜 TLC로 재현하고 수정 후 `끊김`으로 잡히는 것까지 확인했다.

### 응답을 CR/LF까지 이어 읽는다

TCP는 메시지 경계를 보장하지 않는다. 예전에는 `ReadAsync` 한 번으로 끝내서 프레임이 두 조각으로 나뉘면 앞 조각만 파싱 → 체크섬 불일치 → 그 사이클 값 유실이었다. 실기기 42대 동시 접속에서 관측된 3~5% 실패의 일부가 이 경로였을 가능성이 있다.

### 타임아웃은 폴링 주기보다 짧게

기본 1.5초(`Communication:TimeoutMs`). 예전 3초는 폴링 주기(3초)보다 길어서, 한 대만 응답이 없어도 연결 3초 + 응답 3초로 사이클이 6초를 넘고 뒤의 3초 대기까지 더해 실주기가 9초가 됐다 — 대시보드 `api.status`의 주의 기준(10초)에 근접하는 값이다.

### 취소 토큰 연동

타임아웃과 앱 종료를 하나의 `CancellationTokenSource`로 묶었다. 예전 `Task.WhenAny(작업, Task.Delay)` 방식은 정상 응답이어도 타이머가 남고, 버려진 작업이 관찰되지 않은 예외로 끝났으며, 종료 시 최대 6초 매달렸다. 종료 시 나는 `OperationCanceledException`도 더 이상 오류 로그로 남기지 않는다.

## 통신 단절 시 채널값 처리 (사양 확정 2026-09-16)

**1) 끊긴 동안에는 직전 성공값을 그대로 유지한다.**
폴링이 실패하면 `UpdateCurrentValuesAsync`를 아예 호출하지 않으므로(`results.Where(r => r.Ok)`) `CompressorSensorCurrent`가 갱신되지 않고, 마지막 정상 수신값이 남는다. 실패 시 갱신되는 것은 통신 관련 필드뿐이다 — `CommunicationStatus`(연결됨/끊김/재접속중), `DisconnectedSince`, `HasCommunicationAlarm`.

그 결과 **끊김 구간의 채널값은 `null`이 아니다.** 1분 단위 트렌드(`TrendRecordingService`)도 최신값 테이블을 그대로 복사하므로 같은 값이 계속 기록되고, 그래프에서는 평평한 직선으로 보인다. **통신 여부는 값이 아니라 `IsConnected`로 판단해야 한다.**

값이 `null`이 되는 경우는 **그 압축기의 최신값 행이 아예 없을 때**(= 한 번도 통신에 성공한 적 없는 압축기)뿐이다.

**2) 하루가 시작되는데 여전히 끊긴 상태면 전 채널을 0으로 초기화한다.**
`ResetStaleValuesAtDayStartAsync`가 처리한다. 전날 값을 다음 날까지 끌고 가면 "어제 값으로 오늘 하루가 채워지는" 문제가 생기기 때문이다(사용자 결정).

- 판정 기준: 폴링이 실패한 압축기 중 **`MeasuredAt`이 오늘(한국 시간) 00:00 이전**인 채널
- `MeasuredAt`은 일부러 갱신하지 않는다 — 실제 측정 시각이 아니고, 그대로 둬야 다음 사이클에도 같은 판정이 나와 0이 유지된다(이미 0이면 EF가 변경 없음으로 처리해 쓰기도 발생하지 않는다)
- 통신이 복구되면 다음 성공 폴링에서 실제 값으로 덮인다
- 경보 상태(`AlarmStatus`)는 이때 재평가하지 않는다 — 통신 장애는 `HasCommunicationAlarm`으로 별도 관리하기 때문이다
