# RepairLog 모듈 (수리일지)

장비별 수리/보수 작업 내역을 기록하고 결재를 받는 모듈. 장비 관리 화면(장비 이력카드) 하위 기능이다.

혼동 주의 — 이름이 비슷한 다른 문서 모듈들과 전부 별개다:
- `Modules/InspectionReport` (점검일지): 매주 고정 10항목 체크리스트 + 결재 3단계
- `Modules/OperationReport` (운전일지): 일 4회 시점별 자동/수동 기록 + 결재 3단계
- `Modules/EquipmentInspectionHistory` (장비 검사이력): 자유 서술형, 결재 없음

## 내부 구성

- `Controllers/RepairLogsController.cs` — 조회/등록/수정/삭제 + 결재(승인/취소/리셋) API
- `Models/RepairLog.cs` — 엔티티(데이터 11필드 + 작성자/수정자 + 결재 인라인 컬럼 9개)
- `Models/Dtos.cs` — 요청/응답 DTO

## 결재 사양

`Modules/Approval`의 공용 규칙(`ApprovalRules`)을 점검일지와 동일하게 재사용한다. 이 문서유형만의 고정 사양은 레벨별 모드다.

| 레벨 | 역할 | 모드 | 프론트 표시 |
| --- | --- | --- | --- |
| 1 | 안전관리원 | `NotApplicable`(해당없음) | `/` |
| 2 | 안전관리책임자 | `Required` | 대기 / 승인자명 |
| 3 | 안전관리총괄자 | `Required` | 대기 / 승인자명 |

즉 **실제 승인 단계는 안전관리책임자 → 안전관리총괄자 2단계**다. 안전관리원이 승인 API를 호출하면 `409`가 반환된다(결재 대상이 아닌 단계).

공용 규칙에서 그대로 따라오는 것들:
- 순서 강제 — 하위 단계가 완료되기 전에 상위 단계는 승인할 수 없다(`NotApplicable`인 레벨1은 항상 "완료"로 취급되므로 책임자가 곧바로 첫 승인자가 된다).
- 승인 권한은 호출자 본인의 Role + 담당 장비(`UserEquipment`) 기준으로 판정한다 — 그래서 수리일지도 반드시 특정 장비에 매달려야 한다.
- 취소는 본인이 승인한 단계만, 그리고 상위 단계가 아직 승인되지 않았을 때만 가능하다. **반려 개념은 없다.**
- 시스템관리자는 결재를 직접 할 수 없지만, 결재 전체를 무효화(리셋)할 수 있다. 리셋하면 수정 잠금도 함께 풀린다(잠금 판단 기준이 "승인된 단계가 있는지"이므로).
- 승인/취소/리셋은 모두 `EventLog`(Approval 카테고리)에 기록된다.

## 권한 규칙 (사용자 결정)

| 동작 | 결재 진행 전 | 결재가 1건이라도 승인된 후 |
| --- | --- | --- |
| 조회 | 로그인한 사용자 누구나 | 동일 |
| 등록 | 로그인한 사용자 누구나 | — |
| 수정 | 시스템관리자 또는 작성자 | **누구도 불가** (`409`) |
| 삭제 | 시스템관리자 또는 작성자 | **시스템관리자만** (`403`) |

- "결재 완료"가 아니라 **"한 단계라도 승인되면"** 잠긴다(사용자 결정). 승인한 사람이 확인한 내용이 나중에 바뀌는 것을 막기 위한 것으로, 점검일지의 "결재 진행 중 수정 금지"와 같은 원칙이다.
- `CanEdit`/`CanDelete`는 위 표를 요청자 기준으로 계산해서 응답에 담는 값이다(응답 전용). 프론트가 버튼 표시 여부를 판단할 때 쓴다 — 조건이 "결재 상태 + 작성자/관리자" 조합이고, 응답에는 작성자 Id 없이 이름만 있어서 프론트가 자체 판단하기 어렵기 때문이다(검사이력의 `CanEdit`과 같은 이유).

## 사양 이슈 / 결정 이력

- **2026-09-16 결재 레벨1 표기**: 처음 지시는 "안전관리원 = 전결(`//전결`)"이었으나 곧바로 **"해당없음(`/`)"으로 정정**됨. 초기 프론트 화면 사양에 원래 기록돼 있던 내용과 일치한다. 백엔드 동작은 두 모드가 같고(승인 절차 없이 완료 취급) 프론트 표시 문구만 다르다.
- **2026-09-16 첨부파일 미지원 결정**: 첨부파일 공통 규칙에는 원래 수리보수일지도 대상으로 적혀 있었으나, **수리일지는 첨부파일을 지원하지 않기로 사양이 변경**되었다(사용자 결정). 그래서 이 모듈은 `Modules/Attachment`를 쓰지 않고, `AttachmentOwnerType`에도 값을 추가하지 않았다. 나중에 필요해지면 `ownerType=RepairLog`를 추가하고 컨트롤러 분기만 넣으면 된다.
- **필드명 사양 변경**: 초기 프론트 화면 사양의 기록(장소 / 철거 실행자 / 의견)이 실제 사양(수리장소 / 실시자 / 종합의견)과 달라 문서를 갱신했다. 특히 "철거 실행자"는 수리일지 맥락에 맞지 않아 "실시자"로 정리했다.
- **장비 연결 필수**: 데이터 요소 목록에는 장비가 없고 "대상"만 있었으나, 결재 권한이 담당 장비(`UserEquipment`) 기준으로 판정되므로 `EquipmentId`를 필수로 두고 "대상"은 수리 부위를 적는 자유 텍스트로 분리했다(사용자 확인).
- **일시의 타입**: "일시"라는 표현에 맞춰 날짜+시각(`DateTimeOffset`)으로 저장한다. 날짜만 쓰는 검사이력(`DateOnly`)과 다르다.
