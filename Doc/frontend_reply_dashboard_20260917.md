## 먼저 알아야 할 사양 변경 — 운영 상태가 아닌 장비는 노출하지 않음

**장비 상태(`status`)가 `운영`이 아닌 장비는 수집하지 않고 실시간 현황에도 노출하지 않는다**(사양 확정 2026-09-17). 미운영·수리중·점검중·철거예정·철거·사용중지·기타가 모두 해당한다.

| API | 변경 |
|---|---|
| `GET /api/equipments/status` (신규) | `운영` 장비만 |
| `GET /api/compressors` | `운영` 장비의 압축기만 (기존에는 전체) |
| `GET /api/summary` | `운영` 장비와 그 압축기만 센다 (기존에는 전체) |
| `GET /api/equipments`, `GET /api/equipments/{id}` | **변경 없음 — 모든 상태 포함** |

- `GET /api/equipments`는 장비관리 화면에서 상태를 다시 `운영`으로 되돌릴 수 있어야 해서 전체를 유지했다. **실시간 현황, 트렌드, 자료조회처럼 모니터링 화면에서 이 API로 장비 목록(드롭다운 등)을 만든다면 `status === "운영"`으로 걸러야 한다.**
- 운영이 아닌 장비는 1분 트렌드도 기록하지 않는다. 운영이 아니었던 기간은 트렌드 조회 시 빈 구간으로 보인다.
- 운전일지·점검일지에서 이 기준을 어떻게 적용할지는 아직 미정이다(기존 동작 유지).

## 1. `GET /api/system/status`

요청하신 필드 구성 그대로다. 요청 문서와 다르거나 확인이 필요했던 부분만 정리한다.

### 확인 요청 사항에 대한 답

1. **DB 백업**: 현재 백업 기능이 **없다**. `databaseBackup`은 항상 `null`로 온다. 백업 카드는 "-"(또는 "미설정")로 표시해 주세요. 백업 정책이 정해지면 요청 문서의 형태(`lastBackupAt`, `lastBackupSucceeded`, `scheduleText`)로 채운다.
2. **OS 값 읽기 권한**: 운영 서버는 Windows 서비스로 배포된다. CPU·메모리·디스크 모두 관리자 권한 없이 읽히므로 문제없다.
3. **판정 기준**:

| 필드 | `오류` | `주의` | `정상` |
|---|---|---|---|
| `server.status` | 저장소 사용률 95% 이상 | 저장소·메모리·CPU 중 하나라도 90% 이상 | 그 외 |
| `api.status` | DB 연결 실패, 또는 마지막 수집 사이클 완료가 30초 이상 전 | 마지막 수집 사이클 완료가 10초 이상 전 | 그 외 |

### 요청과 의미가 다른 필드

| 필드 | 주의할 점 |
|---|---|
| `collection.compressorCount` | **실제 수집 대상 수**다(운영 장비의 압축기). 요청 예시의 245(전체 압축기 수)와 다를 수 있다. 개발 서버 현재값은 244 |
| `server.startedAt` | **백엔드 프로세스** 시작 시각이다. 서비스를 재시작하면 가동시간이 0부터 다시 시작한다(서버 PC 부팅 시각 아님) |
| `storage.target` | 서버 설정값으로 정한 DB 드라이브. 개발 서버는 `"C:"`이며, 현장 설치 시 운영 서버의 DB 드라이브로 바뀐다 |
| `cpu.usagePercent` | **직전 호출 이후 구간의 평균**이다. 30초마다 부르면 자연히 최근 30초 평균이 된다(요청하신 "순간값 튐 방지") |

### 기타

- 측정 실패 시 해당 객체가 `null`로 오는 규칙은 요청대로 적용했다(`storage`, `cpu`, `memory`, `collection`). `server`와 `api`는 항상 온다.
- **서버 시작 후 첫 호출만** CPU 측정 때문에 0.2~0.3초 정도 더 걸린다(실측 약 0.3초, 이후 호출은 약 0.015초). 응답 시간 표시에서 첫 값만 튈 수 있다.
- 실제 장비 환경에서 응답 없는 압축기가 있으면 수집 사이클이 최대 약 9~10초까지 늘어나 `api.status`가 가끔 `주의`로 보일 수 있다. 현장 설치 후 확인해서 필요하면 기준을 조정할 예정이다.

## 2. `GET /api/equipments/status`

요청 문서의 응답 예시·정렬 규칙 그대로다.

- `운영` 장비만 온다(위 사양 변경 참고). 그래서 이 API에서는 `status`가 항상 `"운영"`이다. 요청 예시와 형태를 맞추려고 필드는 남겨뒀다.
- 개발 서버 실측(장비 105대, 압축기 244대):

| API | 응답 크기 |
|---|---|
| `GET /api/equipments/status` | **약 39 KB** |
| (기존) `GET /api/equipments` + `GET /api/compressors` | 약 127 KB + 약 54 KB |

5초 갱신 기준으로 접속자 1명당 분당 약 2.2 MB에서 약 0.47 MB로 줄어든다.

## 3. `GET /api/compressors` 필드 추가

- `equipmentId`, `sequenceNo`를 추가했다. 기존 필드는 그대로라 기존 코드에는 영향이 없다.
- 단, **이제 `운영` 장비의 압축기만 온다**(위 사양 변경). 이 API로 전체 압축기를 세고 있었다면 결과가 달라질 수 있다.
- 대시보드는 2번 API를 쓰면 이 API를 5초마다 부를 필요가 없다.
