# 현대 남양 연구소 냉동기 모니터링 시스템 개발

## 1. 프로젝트 개요

### 1.1 프로젝트명

**현대 남양 연구소 냉동기 모니터링 시스템 개발**

### 1.2 개발 기간

- 개발 기간: **2026년 8월 ~ 2026년 11월**
- 총 개발 기간: **4개월**

### 1.3 개발 목적

현대 남양 연구소 내에 설치된 냉동 관련 장비와 압축기의 운전 상태 및 센서 정보를 중앙 서버에서 통합 수집하고, 이를 웹 기반 모니터링 시스템을 통해 확인할 수 있도록 한다.

각 장비는 한 대 이상의 압축기로 구성될 수 있으며, 각각의 압축기는 7채널의 센서 정보를 제공한다. 서버는 로컬 이더넷 네트워크를 통해 각 압축기의 실시간 측정값을 수집하고, 경보 판정, 운전 상태 판단, 데이터 저장, 이력 조회 및 비상정지 명령 처리 기능을 수행한다.

본 시스템은 약 20명 내외의 사용자가 이용하는 소규모 내부 시스템을 대상으로 하며, 과도하게 복잡한 시스템보다는 안정적이고 효율적이며 유지보수가 쉬운 구조를 목표로 한다.

## 2. 시스템 구성 개요

전체 시스템은 다음과 같이 구성한다.

```text
장비
 ├─ 압축기 1
 │   └─ 센서 7채널
 ├─ 압축기 2
 │   └─ 센서 7채널
 └─ 압축기 N
     └─ 센서 7채널
          │
          │ 로컬 이더넷 TCP 통신
          ▼
Windows Server
 ├─ 압축기 데이터 수집
 ├─ 프로토콜 처리
 ├─ 실시간 데이터 관리
 ├─ 경보 판정
 ├─ 운전 상태 판정
 ├─ 비상정지 명령 처리
 ├─ 데이터베이스 저장
 ├─ REST API 제공
 └─ 로그 및 이력 관리
          │
          ▼
웹 프론트엔드
 ├─ 실시간 모니터링
 ├─ 트렌드 조회
 ├─ 경보 확인
 ├─ 장비 및 압축기 관리
 ├─ 비상정지
 ├─ 보고서 및 일지
 └─ 게시판
```

## 3. 개발 범위

### 3.1 백엔드 개발

백엔드는 다음 기능을 포함한다.

- 압축기 TCP 통신
- 실시간 센서 데이터 수집
- 압축기별 최신 데이터 관리
- 1분 단위 이력 데이터 생성 및 저장
- 채널별 경보 판정
- 압축기 운전 및 정지 상태 판정
- 비상정지 명령 전송
- 장비 및 압축기 등록 관리
- 사용자 접속 및 주요 동작 이력 관리
- REST API 제공
- 데이터베이스 관리
- 보고서, 점검일지, 운영일지 및 게시판 데이터 관리

### 3.2 개발 기술

- 개발 언어: **C#**
- 백엔드 프레임워크: **ASP.NET Core**
- 실행 환경: **Windows Server**
- 실행 방식: **UI가 없는 Windows Service**
- 통신 방식: **TCP/IP**
- 서버 API: **REST API**
- 데이터베이스: **PostgreSQL**
- 로그 관리: **구조화 로그 기반 파일 및 데이터베이스 저장**
- 개발 도구: **Visual Studio**

### 3.3 시스템 실행 방식

백엔드 프로그램은 별도의 사용자 화면을 제공하지 않는 Windows Service 형태로 개발한다.

- Windows Server 부팅 시 자동 실행
- 사용자 로그인 여부와 관계없이 계속 동작
- 서비스 중지 및 재시작 지원
- 비정상 종료 시 자동 재시작 설정
- 개발 단계에서는 콘솔 모드로 실행 및 디버깅 가능
- 운영 단계에서는 Windows Service로 등록하여 실행

## 4. 주요 요구사항

### 4.1 장비 및 압축기 관리

본 시스템에서는 장비와 압축기를 별도의 관리 대상으로 구분한다.

#### 장비

장비는 현장에 설치된 냉동 관련 설비의 관리 단위이며, 하나의 장비는 한 대 이상의 압축기로 구성될 수 있다.

장비별로 다음 정보를 관리한다.

- 장비ID
- 지역(A지구, B지구, C지구)
- 시설동명
- 장비명칭
- 운영 상태
- 모델명
- 정격전력
- 정격전압
- 압축기 형식
- 압축기 용량
- 냉각탑 형식
- 냉각탑 용량
- 법정 냉동능력
- US 냉동 능력
- 제조년월
- 설치일
- 허가번호
- 사용냉매
- 충전량
- 관리번호(KGS)
- 제조사
- 내압시험압력(HP)
- 내압시험압력(LP)
- 과압차단압력
- 안전밸브 SP(응축기)
- 안전밸브 SP(증발기)
- 운전전류 임계값

장비 운영 상태는 다음과 같이 구분할 수 있다.

- 운영
- 미운영
- 수리 중
- 점검 중
- 철거 예정
- 철거
- 사용 중지
- 기타

장비의 운영 상태가 미운영, 철거 또는 사용 중지 상태인 경우 해당 장비에 소속된 압축기는 기본적으로 데이터 수집 대상에서 제외할 수 있어야 한다.

#### 압축기

압축기는 실제 센서 데이터를 수집하는 통신 대상이다.

압축기별로 다음 정보를 관리한다.

- 압축기 ID
- 소속 장비 ID
- IP 주소
- MAC 주소
- 통신 상태 (연결됨 / 끊김 / 재접속중)
- 경보 상태 (정상 / 경보발생대기 / 경보발생 / 경보확인 / 정상복귀대기 / 경보해제 / 경보비활성화)

압축기 자체는 위 최소한의 정보만 관리한다. 압축기명, TCP 포트, 응답 제한시간, 재접속 주기, 설치 위치, 압축기 설명/사양, 경보 사용 여부 등은 별도 필드로 두지 않으며, 경보 사용 여부를 포함한 세부 설정은 이후 [4.3 센서 채널 관리](#43-센서-채널-관리)에서 채널별로 관리한다. 수집 주기, 통신 프로토콜, 채널 구성(개수 및 정의)은 압축기별 개별 설정 항목이 아니라 시스템 공통 설정을 따른다. 운전전류 임계값 역시 압축기가 아닌 소속 장비 단위로 관리한다. (자세한 내용은 [8.1 데이터 구조 상세](#81-데이터-구조-상세) 참고)

한 장비에는 여러 대의 압축기를 등록할 수 있어야 하며, 각각의 압축기는 독립적으로 통신 상태와 운전 상태를 관리한다.

### 4.2 압축기 데이터 수집

- 전체 압축기는 로컬 네트워크에 연결된다.
- 각 압축기는 고정 IP를 사용한다.
- 서버는 TCP 통신을 통해 압축기 데이터를 읽는다.
- 통신 프로토콜은 ASCII 기반 PC-Link 프로토콜을 사용하며, 국번은 전 압축기 공통으로 01을 사용한다.
- 전체 압축기 수는 최대 약 200대를 기준으로 한다.
- 압축기 데이터 수집 주기는 시스템 공통 설정값(기본 1초)을 사용하며, 압축기별로 개별 설정하지 않는다.
- 압축기별로 독립적인 TCP 통신 세션을 관리한다.
- 특정 압축기의 통신 장애가 다른 압축기 수집에 영향을 주지 않아야 한다.
- 통신 실패 시 자동 재접속 기능을 제공한다.
- 통신 요청, 응답, 타임아웃 및 재접속 상태를 관리한다.
- 비정상 응답 또는 잘못된 패킷 수신 시 해당 내용을 로그로 기록한다.
- 실시간 조회는 RRD(랜덤 읽기) 커맨드로 압축기당 9개 D-Register(7개 센서 채널 + UNUSED 1개 + DOSTS 1개)를 한 번에 읽는다.
- 채널-D-Register 매핑과 프레임 구조 등 프로토콜 전체 내용은 [pclink protocol.md](pclink%20protocol.md)를 참고한다.

### 4.3 센서 채널 관리

각 압축기는 7개의 센서 채널을 가진다.

압축기별 채널 설정(CompressorChannelSetting)에서 관리하는 항목은 다음과 같다.

- 압축기 ID
- 채널 번호 (CH01~CH07, 고정 7개)
- 사용 여부
- 정상 범위 하한값
- 정상 범위 상한값
- 경보 사용 여부
- 경보 발생 지연시간
- 경보 해제 지연시간
- 표시 소수점 자리수

채널 번호(CH01~CH07)별 채널명, 센서 종류, 측정 단위는 압축기별로 다르지 않고 시스템 공통 정의를 따른다 ([8.1 센서 채널 정의](#81-데이터-구조-상세) 참고). 히스테리시스, 경보 등급, 비고는 관리 항목에서 제외했다 — 경보 등급 분류는 도입하지 않기로 확정했다.

압축기 1대는 항상 정확히 7개의 채널 설정 행을 가지며, 압축기 등록 시 CH01~CH07 설정이 함께 생성된다.

### 4.4 실시간 데이터 관리

- 압축기에서 수집한 최신 센서값은 `CompressorSensorCurrent` 테이블에 압축기·채널당 1행으로 유지(UPSERT)한다.
- 사용자 20명, 2~3초 폴링 규모에서는 요청마다 DB를 직접 조회해도 충분하다. 별도의 메모리 캐시 계층은 두지 않는다 (트래픽이 실제로 문제가 될 때 재검토).
- 압축기별 최신 측정 시각을 관리한다.
- 압축기별 통신 상태를 제공한다.
- 압축기별 운전 및 정지 상태를 제공한다.
- 압축기별 현재 경보 상태를 제공한다.
- 프론트엔드는 REST API를 통해 최신값을 조회한다.
- 초기 시스템은 2~3초 주기의 REST Polling 방식으로 구현하는 것을 기본으로 한다.
- 향후 필요 시 SignalR 기반 실시간 전송 기능을 추가할 수 있도록 확장성을 고려한다.

### 4.5 이력 데이터 저장 (DailyTrend)

압축기별 7채널 센서 정보는 1분 단위로 저장한다. 이 1분 단위 트렌드 이력을 DailyTrend라 한다.

- 매 분 정각마다 장비에 속한 모든 압축기의 CH01~CH07 채널값을 기록한다.
- 하루 기준 기록 규모는 장비 단위로 "압축기 수 × 7채널 × 60분 × 24시간(1,440분)"이다.
- 자정이 되면 해당 장비는 새로운 날짜의 DailyTrend 기록을 새로 시작한다.
- 전류값, 운전 상태, 경보 상태 및 통신 상태도 함께 저장할 수 있다.
- 저장 시간은 서버의 정각 기준으로 관리한다.
- 예: 10:00, 10:01, 10:02
- 수집 시각 기준 1분 동안의 평균값, 최소값, 최대값 또는 마지막값 저장 여부는 추후 결정한다.
- 기본 저장 방식은 1분 대표값을 저장하는 방식으로 한다.
- 트렌드 조회 시 압축기별, 채널별, 날짜별 데이터 조회가 가능해야 한다.
- 장기간 데이터 보관을 고려하여 날짜 및 압축기 기준 인덱스를 구성한다.
- 데이터 보관 기간과 백업 정책은 추후 결정한다.

세부 테이블 구조는 [8.1 데이터 구조 상세](#81-데이터-구조-상세)를 참고한다.

### 4.6 경보 관리

각 압축기의 7채널은 개별적으로 경보 설정이 가능해야 한다.

#### 경보 발생 조건

- 센서값이 설정된 정상 범위 상한값을 초과한 경우
- 센서값이 설정된 정상 범위 하한값 미만인 경우
- 설정된 경보 발생 지연시간 이상 비정상 상태가 지속된 경우
- 통신 장애가 설정된 시간 이상 지속된 경우
- 센서값이 유효 범위를 벗어나거나 비정상 데이터로 판단된 경우

#### 경보 발생 지연

센서값이 일시적으로 정상 범위를 벗어나는 경우 불필요한 경보가 발생하지 않도록 경보 발생 지연시간을 설정할 수 있어야 한다.

예:

```text
정상 범위: -20℃ ~ -10℃
경보 발생 지연: 10초
```

센서값이 정상 범위를 벗어난 상태로 10초 이상 지속된 경우에만 경보를 발생시킨다.

#### 경보 해제 지연

센서값이 정상 범위로 복귀하더라도 설정된 시간 이상 정상 상태가 유지된 후 경보를 해제할 수 있어야 한다.

#### 히스테리시스

센서값이 경계값 부근에서 반복적으로 변할 경우 경보 발생과 해제가 반복되는 현상을 방지하기 위해 히스테리시스 값을 설정할 수 있어야 한다.

#### 압축기 경보 끄기

압축기별로 경보 기능을 끌 수 있어야 한다.

- 경보 끄기 상태에서는 해당 압축기의 채널값이 정상 범위를 벗어나더라도 신규 경보를 발생시키지 않는다.
- 데이터 수집과 이력 저장은 계속 수행한다.
- 경보 기능이 비활성화된 상태임을 화면과 로그에서 확인할 수 있어야 한다.
- 경보 끄기 및 다시 켜기 작업은 사용자 동작 이력에 기록해야 한다.

#### 경보 상태

경보는 다음 상태를 가질 수 있다.

- 정상
- 경보 발생 대기
- 경보 발생
- 정상 복귀 대기
- 경보 비활성화

**경보 확인 기능은 시스템 사양에 없다.** 로그인 사용자에 의한 확인 절차를 두지 않으며, 경보가 발생하면 값이 정상 범위로 돌아올 때까지(정상 복귀 대기 → 정상) 별도 조작 없이 경보 발생 상태를 그대로 유지한다. "경보 해제"도 별도로 유지되는 상태가 아니라 정상 복귀 대기가 끝나면 바로 정상으로 전환된다.

경보 이벤트는 단순 문자열이 아닌 구조화된 데이터로 저장한다. 세부 항목은 [8.1 데이터 구조 상세](#81-데이터-구조-상세)를 참고한다.

### 4.7 운전 및 정지 상태 판단

냉동 장비의 운전 여부는 장비(Equipment) 단위로 설정된 운전전류 임계값과 각 압축기의 CH07(운전전류) 측정값을 비교하여 판단한다.

- 운전전류 임계값은 압축기별이 아닌 장비 단위로 하나만 설정한다.
- 판정 대상 채널은 CH07(운전전류)로 고정하며, 압축기별로 다른 채널을 지정하지 않는다.
- 장비에 속한 압축기 중 다음 조건을 만족하는 압축기가 하나라도 있으면 해당 장비를 운전(Running) 상태로 판단한다.

```text
CH07.사용 여부 == true
AND
CH07 측정값 > 장비의 운전전류 임계값
```

- CH07 채널이 비활성화(사용 여부 = false)된 압축기는 운전 판정 대상에서 제외한다.
- 조건을 만족하는 압축기가 하나도 없으면 장비는 정지(Stopped) 상태로 판단한다.
- 운전 시작 및 운전 정지 시각을 기록한다.
- 압축기별 누적 운전시간 관리 여부는 추후 결정한다.
- 장비별 또는 압축기별 가동률 산출 여부는 추후 결정한다.

### 4.8 비상정지 기능

프론트엔드에서 압축기에 비상정지 명령을 전송할 수 있어야 한다.

비상정지 기능은 TCP 프로토콜의 DO(Digital Output) 접점 쓰기 명령을 통해 수행한다. 실제 TLC 프로토콜에서 제공하는 쓰기 기능은 이 DO 접점 쓰기가 유일하다.

내부적으로는 WRD(랜덤 쓰기) 커맨드로 DOSTS(D1805) 레지스터의 현재 DO 상태를 읽어온 뒤 특정 비트(`EmgStopBit`)만 변경해 다시 쓰는 read-modify-write 방식으로 구현한다. `EmgStopBit`의 정확한 비트 위치는 아직 확정되지 않았다. 상세 커맨드 예시는 [pclink protocol.md](pclink%20protocol.md)를 참고한다.

#### 비상정지 처리 절차

```text
사용자 비상정지 요청
      ↓
사용자 권한 확인
      ↓
대상 장비 및 압축기 확인
      ↓
사용자 재확인
      ↓
서버에서 TCP 쓰기 명령 전송
      ↓
압축기 응답 확인
      ↓
처리 결과 저장 및 로그 기록
```

#### 비상정지 요구사항

- 비상정지 기능은 권한이 부여된 사용자만 수행할 수 있어야 한다.
- 사용자의 단순 오조작을 방지하기 위한 재확인 절차가 필요하다.
- 대상 장비명, 압축기명, 위치 및 현재 운전 상태를 확인한 후 수행해야 한다.
- 비상정지 명령 요청 시각을 기록해야 한다.
- 명령을 수행한 사용자 정보를 기록해야 한다.
- TCP로 전송한 명령 정보를 기록해야 한다.
- 명령 전송 성공 및 실패 여부를 기록해야 한다.
- 압축기 응답 결과를 기록해야 한다.
- 명령 수행 후 실제 운전 상태가 정지로 변경되었는지 확인해야 한다.
- 쓰기 명령의 중복 실행을 방지해야 한다.
- 통신 장애 상태에서는 비상정지 명령을 제한하거나 경고해야 한다.
- 비상정지 해제(재운전)는 동일한 DOSTS 비트 토글 방식으로 기술적으로 가능하나, 해제 시 별도 권한/재확인 절차를 요구할지 등 정책은 추후 결정한다.

## 5. 로그 및 이벤트 관리

시스템 규모(약 20명 사용자, 단일 서버)를 고려하여 로그는 별도의 로깅 프레임워크 없이 단순한 이벤트 기록 방식으로 관리한다. 다음 4가지 이벤트를 기록 대상으로 한다.

1. 사용자 접속(로그인/로그아웃) 및 비상정지 수행 — 시스템에서 발생하는 유일한 쓰기/제어 동작
2. 압축기 통신 불능 및 복구 — 통신 상태가 실제로 변경된 시점만 기록 (예: 부팅 시 재시도 반복 후 최종 실패, 이후 복구)
3. 경보 발생 — 장비명, 압축기, 채널(상한/하한 여부) 기준
4. 시스템 시작 및 오류

### 5.1 저장 방식

- 위 4가지 이벤트는 하나의 이벤트 로그 테이블(EventLog)에 카테고리로 구분하여 저장한다.
- 카테고리: `UserAccess`(접속) / `EmergencyStop`(비상정지) / `Communication`(통신) / `Alarm`(경보) / `System`(시스템)
- 별도 로깅 라이브러리(Serilog 등) 도입 없이 .NET 기본 로깅(`ILogger`)과 DB 저장만으로 구현한다.
- 시스템 시작 오류, DB 연결 실패처럼 DB에 기록할 수 없는 시점의 이벤트는 콘솔/기본 로그 경로로도 남긴다.

### 5.2 이벤트 로그 항목

- 발생 시각
- 카테고리
- 레벨 (정보/경고/오류)
- 메시지
- 관련 사용자 ID (해당 시)
- 관련 장비/압축기 ID (해당 시)
- 상세 내용 (측정값, 상한/하한값 등 필요 시)

### 8.1 데이터 구조 상세

기본 설비 구조와 데이터 관계는 다음과 같다.

```text
Equipment(장비) 1 ── N Compressor(압축기)
Compressor(압축기) 1 ── 7 CompressorChannelSetting(채널 설정)
Compressor(압축기) 1 ── N CompressorMeasurement(DailyTrend 이력)
Compressor(압축기) 1 ── N Alarm/Event
Equipment(장비) 1 ── N EquipmentUser(담당자)
User(사용자) 1 ── N EquipmentUser(담당자)
```

#### 시스템 공통 설정

다음 항목은 압축기마다 개별 관리하지 않고 시스템 전체 공통값으로 관리한다.

| 항목               | 기본값  | 설명                                      |
| ------------------ | ------- | ----------------------------------------- |
| 통신 방식          | TCP     | TLC와 Ethernet TCP 통신                   |
| 프로토콜           | PC-Link | ASCII 기반 PC-Link 프로토콜               |
| 국번               | 01      | 모든 TLC 통신에 동일하게 사용             |
| Polling Interval   | 1000ms  | 전 압축기 공통 수집 주기 (개별 설정 불가) |
| Channel Count      | 7       | 압축기당 고정 채널 수                     |
| Channel Definition | 고정    | CH01~CH07 공통 정의                       |

#### 센서 채널 정의 (공통)

| Channel | 센서     | 단위 | 설명               |
| ------- | -------- | ---- | ------------------ |
| CH01    | 저온     | ℃    | 압축기 흡입측 온도 |
| CH02    | 고온     | ℃    | 압축기 토출측 온도 |
| CH03    | 오일온도 | ℃    | 압축기 오일 온도   |
| CH04    | 저압     | MPa  | 압축기 저압        |
| CH05    | 고압     | MPa  | 압축기 고압        |
| CH06    | 오일압력 | MPa  | 오일압력           |
| CH07    | 운전전류 | A    | 운전구동 전류      |

채널 정의는 전 압축기 공통이며, 압축기별로는 채널의 사용 여부와 경보 상/하한값 등만 개별 관리한다([4.3 센서 채널 관리](#43-센서-채널-관리) 참고). 사용 여부가 false인 채널은 유효성 판단, 경보 판정, 상태 판정에서 제외한다.

실제 TLC(PC-Link) 프로토콜에서 제공하는 기능은 위 7개 채널 읽기와 비상정지를 위한 DO(Digital Output) 접점 쓰기가 전부이며, 그 외 추가 센서 채널이나 다른 쓰기 명령은 제공되지 않는다.

#### 상태 판정 (압축기 → 장비 집계)

장비의 운전/경보/통신 상태는 소속 압축기 상태를 집계하여 계산한다.

- **운전 상태**: 장비 단위 운전전류 임계값과 CH07 비교, 압축기 중 하나라도 조건을 만족하면 장비는 Running. 세부 로직은 [4.7 운전 및 정지 상태 판단](#47-운전-및-정지-상태-판단) 참고.
- **경보 상태**: 활성 채널 중 하나라도 상/하한을 벗어나면 해당 압축기 경보, 소속 압축기 중 하나라도 경보 상태면 장비는 Alarm. 지연시간·상태 단계 등 세부 판정 로직은 [4.6 경보 관리](#46-경보-관리) 참고.
- **통신 상태**: 압축기 하나라도 통신 불능이면 장비는 Fault, 전 압축기 정상 통신 시 장비는 Normal.

#### 실시간 데이터 구조

프론트엔드 조회 성능을 위해 다음 실시간 상태를 메모리 및 캐시성 테이블로 관리한다.

- `CompressorSensorCurrent` — 압축기·채널별 최신값(Value, MeasuredAt). 새 값 수집 시 갱신(UPSERT)하며 이력이 아닌 현재값 유지 용도. 채널별로 정확히 1행만 존재하며(압축기당 7행 고정) 누적되지 않는다. 채널 사용 여부(Enabled)와 무관하게 원시값은 항상 갱신한다.
- `CompressorRealtimeStatus` — 압축기 단위 최신 상태(통신/경보/운전 상태, 최근 통신·측정 시각)
- `EquipmentRealtimeStatus` — 장비 단위 최신 상태(소속 압축기 집계 결과)

#### 이력 데이터 구조 (DailyTrend)

[4.5 이력 데이터 저장](#45-이력-데이터-저장-dailytrend) 참고. 한 번의 Polling에서 7채널을 함께 읽으므로, 하나의 측정 시점을 하나의 Row로 저장(채널을 컬럼으로 전개)하는 방식을 우선 검토한다.

```text
CompressorMeasurement (DailyTrend)
- Id
- CompressorId
- MeasuredAt
- Ch01 ~ Ch07
```

#### 경보 이벤트 구조

경보 발생 시 문자열이 아닌 구조화된 데이터로 저장한다.

```text
Alarm / Event
- EquipmentId
- CompressorId
- ChannelNo
- AlarmType (High / Low)
- MeasuredValue
- ThresholdValue
- OccurredAt
- RecoveredAt
```

구조화된 이벤트 데이터는 향후 경보 이력 조회, 기간별/장비별/압축기별 경보 통계, 센서별 빈발 경보 분석, 정비 보고서 자동 생성 등에 활용할 수 있다.

#### 사용자와 담당 장비

장비별 담당자는 Equipment에 직접 저장하지 않고 별도 관계 테이블로 관리한다(주담당/부담당 등 역할 확장, 다대다 관계 고려).

```text
EquipmentUser
- EquipmentId
- UserId
- Role
```

#### 장비/압축기 등록 및 설정 변경 반영

- 신규 압축기 등록 시 CH01~CH07 채널 설정(ChannelSetting)을 자동 생성한다. 채널 개수(7개)는 시스템 공통 규칙으로 고정하며, 개별 채널값은 이후 웹에서 수정 가능하다.
- 백엔드 시작 시 DB에서 활성 장비/압축기 목록을 조회하여 Polling을 시작한다.
- 실행 중 웹에서 압축기가 추가되거나 IP가 변경되는 경우 프로그램 재시작 없이 Polling Manager가 반영한다(IP 변경 시 기존 연결 종료 후 재연결, 삭제/비활성화 시 Polling 중단).

#### 데이터 설계 원칙

1. 장비와 압축기를 명확하게 분리한다.
2. IP 주소는 통신 단위인 압축기에서 관리한다.
3. 공통 통신 설정(프로토콜, 국번, Polling Interval, 채널 수/정의)은 개별 압축기에 중복 저장하지 않고 시스템 공통으로 관리한다.
4. 센서의 설치 여부(사용 여부)와 경보 임계값은 압축기별 채널 설정에서 관리한다.
5. 운전전류 임계값은 압축기가 아닌 장비 단위로 관리한다.
6. 압축기 상태와 장비 상태를 구분하며, 장비 상태는 소속 압축기 상태를 집계하여 계산한다.
7. 현재값(실시간)과 이력 데이터를 분리하여 관리한다.
8. 경보 데이터는 문자열이 아닌 구조화된 데이터로 저장한다.
9. 장비 구성 변경(등록/IP 변경/비활성화)은 서버 재시작 없이 Polling에 반영한다.

## 9. 개발 방법론

### 9.1 개발 기본 방향

본 프로젝트는 소규모 사용자와 단일 서버 환경을 기준으로 하므로, 복잡한 마이크로서비스 구조는 적용하지 않는다.

하나의 ASP.NET Core 백엔드 프로그램이 다음 기능을 통합 수행하도록 한다.

- TCP 데이터 수집
- 데이터 처리
- 경보 판정
- 운전 상태 판정
- 데이터베이스 저장
- REST API 제공
- 사용자 인증 및 권한 관리
- 보고서 및 게시판 데이터 관리

Redis, Kafka, RabbitMQ 및 Kubernetes 등의 별도 인프라는 초기 구축 범위에서 제외한다.

## 11. 비기능 요구사항

### 11.1 성능

- 최대 약 200대의 압축기를 지원해야 한다.
- 시스템 공통 설정 기준 1~2초 주기의 데이터 수집을 지원해야 한다.
- 약 20명의 동시 사용자가 안정적으로 시스템을 이용할 수 있어야 한다.
- 실시간 데이터 API는 일반적인 내부망 환경에서 빠르게 응답해야 한다.
- 트렌드 조회는 지정된 압축기와 기간 기준으로 수행한다.

### 11.2 안정성

- 특정 압축기의 통신 실패가 전체 수집에 영향을 주지 않아야 한다.
- 데이터베이스 장애 발생 시 수집 프로그램 전체가 종료되지 않아야 한다.
- 서비스 비정상 종료 시 자동 재시작할 수 있어야 한다.
- 서버 재부팅 후 자동으로 데이터 수집을 재개해야 한다.
- 통신 복구 후 자동으로 정상 수집 상태로 전환되어야 한다.

### 11.3 보안

- 사용자 로그인 기능을 제공해야 한다.
- 사용자별 권한을 적용해야 한다.
- 비상정지 기능은 별도 권한을 가진 사용자만 수행할 수 있어야 한다.
- 비상정지 및 주요 설정 변경은 감사 로그에 기록해야 한다.
- 비밀번호는 안전한 방식으로 암호화하여 저장해야 한다.
- 내부망 시스템이라도 주요 API는 인증 없이 호출할 수 없도록 한다.
- HTTPS 적용 여부는 서버 운영 정책에 따라 결정한다.

### 11.4 유지보수성

- 장비와 압축기를 프로그램 수정 없이 등록 및 변경할 수 있어야 한다.
- 채널 및 경보 기준값을 프로그램 수정 없이 변경할 수 있어야 한다.
- 로그를 통해 통신, 경보, 시스템 오류를 추적할 수 있어야 한다.
- 프로토콜 변경에 대응할 수 있도록 통신부와 프로토콜 해석부를 분리한다.
- 보고서와 일지 기능은 향후 항목 추가가 가능하도록 설계한다.

## 12. 추후 결정 필요사항

다음 항목은 상세 협의 후 확정한다.

- 실제 압축기 수량
- 장비 한 대당 최대 압축기 수
- TCP 연결 유지 또는 매 요청 연결 방식
- 비상정지 DOSTS 비트 위치(`EmgStopBit`) 확정
- 비상정지 해제(재운전) 시 권한/재확인 절차 필요 여부
- 1분 이력 데이터의 평균값, 최소값, 최대값 및 마지막값 저장 여부
- 데이터 보관 기간
- 데이터 백업 및 복원 정책
- 통신 장애 경보 기준시간
- 누적 운전시간 및 가동률 산출 여부
- DailyTrend 이력 테이블의 날짜별 파티셔닝 전략 상세
- 보고서 승인 절차
- 교육훈련 레포트 세부 항목
- 점검일지 세부 항목
- 운영일지 세부 항목
- 첨부파일 허용 형식 및 최대 용량
- 사용자 권한 단계
- Active Directory 연동 여부
- 이메일 또는 문자 경보 알림 여부
- HTTPS 및 서버 인증서 적용 여부
- 프론트엔드 실시간 데이터 갱신 방식
