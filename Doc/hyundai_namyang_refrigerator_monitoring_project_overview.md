# 현대 남양 연구소 냉동기 모니터링 시스템 개발

## 1. 프로젝트 개요

### 1.1 프로젝트명

**현대 남양 연구소 냉동기 모니터링 시스템 개발**

### 1.2 개발 기간

- 개발 기간: **2026년 8월 ~ 2026년 11월**
- 총 개발 기간: **4개월**

### 1.3 개발 목적

현대 남양 연구소 내에 설치된 냉동 관련 장비와 압축기의 운전 상태 및 센서 정보를 중앙 서버에서 통합 수집하고, 이를 웹 기반 모니터링 시스템을 통해 확인할 수 있도록 한다.

각 장비는 한 대 이상의 압축기로 구성될 수 있으며, 각각의 압축기는 12채널의 센서 정보를 제공한다. 서버는 로컬 이더넷 네트워크를 통해 각 압축기의 실시간 측정값을 수집하고, 경보 판정, 운전 상태 판단, 데이터 저장, 이력 조회 및 비상정지 명령 처리 기능을 수행한다.

본 시스템은 약 20명 내외의 사용자가 이용하는 소규모 내부 시스템을 대상으로 하며, 과도하게 복잡한 시스템보다는 안정적이고 효율적이며 유지보수가 쉬운 구조를 목표로 한다.

## 2. 시스템 구성 개요

전체 시스템은 다음과 같이 구성한다.

```text
장비
 ├─ 압축기 1
 │   └─ 센서 12채널
 ├─ 압축기 2
 │   └─ 센서 12채널
 └─ 압축기 N
     └─ 센서 12채널
          │
          │ 로컬 이더넷 TCP 통신
          ▼
Windows Server
 ├─ 압축기 데이터 수집
 ├─ 프로토콜 처리
 ├─ 실시간 데이터 관리
 ├─ 경보 판정
 ├─ 운전 상태 판정
 ├─ 비상정지 명령 처리
 ├─ 데이터베이스 저장
 ├─ REST API 제공
 └─ 로그 및 이력 관리
          │
          ▼
웹 프론트엔드
 ├─ 실시간 모니터링
 ├─ 트렌드 조회
 ├─ 경보 확인
 ├─ 장비 및 압축기 관리
 ├─ 비상정지
 ├─ 보고서 및 일지
 └─ 게시판
```

## 3. 개발 범위

### 3.1 백엔드 개발

백엔드는 다음 기능을 포함한다.

- 압축기 TCP 통신
- 실시간 센서 데이터 수집
- 압축기별 최신 데이터 관리
- 1분 단위 이력 데이터 생성 및 저장
- 채널별 경보 판정
- 압축기 운전 및 정지 상태 판정
- 비상정지 명령 전송
- 장비 및 압축기 등록 관리
- 사용자 접속 및 주요 동작 이력 관리
- REST API 제공
- 데이터베이스 관리
- 보고서, 점검일지, 운영일지 및 게시판 데이터 관리

### 3.2 개발 기술

- 개발 언어: **C#**
- 백엔드 프레임워크: **ASP.NET Core**
- 실행 환경: **Windows Server**
- 실행 방식: **UI가 없는 Windows Service**
- 통신 방식: **TCP/IP**
- 서버 API: **REST API**
- 데이터베이스: **SQL Server 또는 PostgreSQL**
- 로그 관리: **구조화 로그 기반 파일 및 데이터베이스 저장**
- 개발 도구: **Visual Studio**

### 3.3 시스템 실행 방식

백엔드 프로그램은 별도의 사용자 화면을 제공하지 않는 Windows Service 형태로 개발한다.

- Windows Server 부팅 시 자동 실행
- 사용자 로그인 여부와 관계없이 계속 동작
- 서비스 중지 및 재시작 지원
- 비정상 종료 시 자동 재시작 설정
- 개발 단계에서는 콘솔 모드로 실행 및 디버깅 가능
- 운영 단계에서는 Windows Service로 등록하여 실행

## 4. 주요 요구사항

### 4.1 장비 및 압축기 관리

본 시스템에서는 장비와 압축기를 별도의 관리 대상으로 구분한다.

#### 장비

장비는 현장에 설치된 냉동 관련 설비의 관리 단위이며, 하나의 장비는 한 대 이상의 압축기로 구성될 수 있다.

장비별로 다음 정보를 관리한다.

- 장비 ID
- 장비명
- 장비 설명
- 시설동명
- 설치 위치
- 용량
- 설치 날짜
- 운영 상태
- 담당자
- 담당자 연락처
- 장비 사양
- 비고
- 등록일
- 수정일

장비 운영 상태는 다음과 같이 구분할 수 있다.

- 운영
- 미운영
- 수리 중
- 점검 중
- 철거 예정
- 철거
- 사용 중지
- 기타

장비의 운영 상태가 미운영, 철거 또는 사용 중지 상태인 경우 해당 장비에 소속된 압축기는 기본적으로 데이터 수집 대상에서 제외할 수 있어야 한다.

#### 압축기

압축기는 실제 센서 데이터를 수집하는 통신 대상이다.

압축기별로 다음 정보를 관리한다.

- 압축기 ID
- 소속 장비 ID
- 압축기명
- IP 주소
- TCP 포트
- 통신 사용 여부
- 수집 주기
- 응답 제한시간
- 재접속 주기
- 설치 위치
- 압축기 설명
- 압축기 사양
- 운전 판단용 전류 채널
- 운전 시작 기준값
- 운전 정지 기준값
- 경보 사용 여부
- 운영 상태
- 등록일
- 수정일

한 장비에는 여러 대의 압축기를 등록할 수 있어야 하며, 각각의 압축기는 독립적으로 통신 상태와 운전 상태를 관리한다.

### 4.2 압축기 데이터 수집

- 전체 압축기는 로컬 네트워크에 연결된다.
- 각 압축기는 고정 IP를 사용한다.
- 서버는 TCP 통신을 통해 압축기 데이터를 읽는다.
- 통신 프로토콜은 사전에 정의된 전용 프로토콜을 사용한다.
- 전체 압축기 수는 최대 약 200대를 기준으로 한다.
- 압축기별 데이터 수집 주기는 약 1~2초로 한다.
- 압축기별로 독립적인 TCP 통신 세션을 관리한다.
- 특정 압축기의 통신 장애가 다른 압축기 수집에 영향을 주지 않아야 한다.
- 통신 실패 시 자동 재접속 기능을 제공한다.
- 통신 요청, 응답, 타임아웃 및 재접속 상태를 관리한다.
- 비정상 응답 또는 잘못된 패킷 수신 시 해당 내용을 로그로 기록한다.

### 4.3 센서 채널 관리

각 압축기는 12개의 센서 채널을 가진다.

채널별로 다음 정보를 관리한다.

- 채널 번호
- 채널명
- 센서 종류
- 측정 단위
- 표시 소수점 자리수
- 사용 여부
- 정상 범위 하한값
- 정상 범위 상한값
- 경보 사용 여부
- 경보 발생 지연시간
- 경보 해제 지연시간
- 히스테리시스 값
- 경보 등급
- 비고

센서 채널은 압축기별로 독립적인 설정이 가능해야 한다.

### 4.4 실시간 데이터 관리

- 압축기에서 수집한 최신 센서값은 서버 메모리에 유지한다.
- 실시간값은 데이터베이스를 매번 조회하지 않고 메모리의 최신값을 통해 제공한다.
- 압축기별 최신 측정 시각을 관리한다.
- 압축기별 통신 상태를 제공한다.
- 압축기별 운전 및 정지 상태를 제공한다.
- 압축기별 현재 경보 상태를 제공한다.
- 프론트엔드는 REST API를 통해 최신값을 조회한다.
- 초기 시스템은 2~3초 주기의 REST Polling 방식으로 구현하는 것을 기본으로 한다.
- 향후 필요 시 SignalR 기반 실시간 전송 기능을 추가할 수 있도록 확장성을 고려한다.

### 4.5 이력 데이터 저장

압축기별 12채널 센서 정보는 1분 단위로 저장한다.

- 압축기당 하루 1,440개의 시점 데이터를 저장한다.
- 각 시점 데이터에는 12채널 센서값이 포함된다.
- 전류값, 운전 상태, 경보 상태 및 통신 상태도 함께 저장할 수 있다.
- 저장 시간은 서버의 정각 기준으로 관리한다.
- 예: 10:00, 10:01, 10:02
- 수집 시각 기준 1분 동안의 평균값, 최소값, 최대값 또는 마지막값 저장 여부는 추후 결정한다.
- 기본 저장 방식은 1분 대표값을 저장하는 방식으로 한다.
- 트렌드 조회 시 압축기별, 채널별, 날짜별 데이터 조회가 가능해야 한다.
- 장기간 데이터 보관을 고려하여 날짜 및 압축기 기준 인덱스를 구성한다.
- 데이터 보관 기간과 백업 정책은 추후 결정한다.

### 4.6 경보 관리

각 압축기의 12채널은 개별적으로 경보 설정이 가능해야 한다.

#### 경보 발생 조건

- 센서값이 설정된 정상 범위 상한값을 초과한 경우
- 센서값이 설정된 정상 범위 하한값 미만인 경우
- 설정된 경보 발생 지연시간 이상 비정상 상태가 지속된 경우
- 통신 장애가 설정된 시간 이상 지속된 경우
- 센서값이 유효 범위를 벗어나거나 비정상 데이터로 판단된 경우

#### 경보 발생 지연

센서값이 일시적으로 정상 범위를 벗어나는 경우 불필요한 경보가 발생하지 않도록 경보 발생 지연시간을 설정할 수 있어야 한다.

예:

```text
정상 범위: -20℃ ~ -10℃
경보 발생 지연: 10초
```

센서값이 정상 범위를 벗어난 상태로 10초 이상 지속된 경우에만 경보를 발생시킨다.

#### 경보 해제 지연

센서값이 정상 범위로 복귀하더라도 설정된 시간 이상 정상 상태가 유지된 후 경보를 해제할 수 있어야 한다.

#### 히스테리시스

센서값이 경계값 부근에서 반복적으로 변할 경우 경보 발생과 해제가 반복되는 현상을 방지하기 위해 히스테리시스 값을 설정할 수 있어야 한다.

#### 압축기 경보 끄기

압축기별로 경보 기능을 끌 수 있어야 한다.

- 경보 끄기 상태에서는 해당 압축기의 채널값이 정상 범위를 벗어나더라도 신규 경보를 발생시키지 않는다.
- 데이터 수집과 이력 저장은 계속 수행한다.
- 경보 기능이 비활성화된 상태임을 화면과 로그에서 확인할 수 있어야 한다.
- 경보 끄기 및 다시 켜기 작업은 사용자 동작 이력에 기록해야 한다.

#### 경보 상태

경보는 다음 상태를 가질 수 있다.

- 정상
- 경보 발생 대기
- 경보 발생
- 경보 확인
- 정상 복귀 대기
- 경보 해제
- 경보 비활성화

### 4.7 운전 및 정지 상태 판단

압축기의 전류값을 기준으로 운전 여부를 판단한다.

- 전류값이 운전 시작 기준값 이상이면 운전 상태로 판단한다.
- 전류값이 운전 정지 기준값 미만이면 정지 상태로 판단한다.
- 운전 시작 기준값과 운전 정지 기준값은 서로 다르게 설정할 수 있어야 한다.
- 경계값 부근에서 운전과 정지가 반복되지 않도록 히스테리시스를 적용한다.
- 일정 시간 이상 상태가 지속된 후 운전 또는 정지 상태를 확정할 수 있어야 한다.
- 운전 시작 및 운전 정지 시각을 기록한다.
- 압축기별 누적 운전시간 관리 여부는 추후 결정한다.
- 장비별 또는 압축기별 가동률 산출 여부는 추후 결정한다.

### 4.8 비상정지 기능

프론트엔드에서 압축기에 비상정지 명령을 전송할 수 있어야 한다.

비상정지 기능은 TCP 프로토콜의 쓰기 명령을 통해 수행한다.

#### 비상정지 처리 절차

```text
사용자 비상정지 요청
      ↓
사용자 권한 확인
      ↓
대상 장비 및 압축기 확인
      ↓
사용자 재확인
      ↓
서버에서 TCP 쓰기 명령 전송
      ↓
압축기 응답 확인
      ↓
처리 결과 저장 및 로그 기록
```

#### 비상정지 요구사항

- 비상정지 기능은 권한이 부여된 사용자만 수행할 수 있어야 한다.
- 사용자의 단순 오조작을 방지하기 위한 재확인 절차가 필요하다.
- 대상 장비명, 압축기명, 위치 및 현재 운전 상태를 확인한 후 수행해야 한다.
- 비상정지 명령 요청 시각을 기록해야 한다.
- 명령을 수행한 사용자 정보를 기록해야 한다.
- TCP로 전송한 명령 정보를 기록해야 한다.
- 명령 전송 성공 및 실패 여부를 기록해야 한다.
- 압축기 응답 결과를 기록해야 한다.
- 명령 수행 후 실제 운전 상태가 정지로 변경되었는지 확인해야 한다.
- 쓰기 명령의 중복 실행을 방지해야 한다.
- 통신 장애 상태에서는 비상정지 명령을 제한하거나 경고해야 한다.
- 비상정지 해제 또는 재운전 명령 제공 여부는 추후 결정한다.

## 5. 로그 및 감사 이력 관리

로그는 용도에 따라 다음과 같이 분류한다.

### 5.1 시스템 로그

백엔드 서비스와 시스템 전반의 동작 상태를 기록한다.

- 프로그램 시작
- 프로그램 종료
- 서비스 재시작

## 11. 비기능 요구사항

### 11.1 성능

- 최대 약 200대의 압축기를 지원해야 한다.
- 압축기별 1~2초 주기의 데이터 수집을 지원해야 한다.
- 약 20명의 동시 사용자가 안정적으로 시스템을 이용할 수 있어야 한다.
- 실시간 데이터 API는 일반적인 내부망 환경에서 빠르게 응답해야 한다.
- 트렌드 조회는 지정된 압축기와 기간 기준으로 수행한다.

### 11.2 안정성

- 특정 압축기의 통신 실패가 전체 수집에 영향을 주지 않아야 한다.
- 데이터베이스 장애 발생 시 수집 프로그램 전체가 종료되지 않아야 한다.
- 서비스 비정상 종료 시 자동 재시작할 수 있어야 한다.
- 서버 재부팅 후 자동으로 데이터 수집을 재개해야 한다.
- 통신 복구 후 자동으로 정상 수집 상태로 전환되어야 한다.

### 11.3 보안

- 사용자 로그인 기능을 제공해야 한다.
- 사용자별 권한을 적용해야 한다.
- 비상정지 기능은 별도 권한을 가진 사용자만 수행할 수 있어야 한다.
- 비상정지 및 주요 설정 변경은 감사 로그에 기록해야 한다.
- 비밀번호는 안전한 방식으로 암호화하여 저장해야 한다.
- 내부망 시스템이라도 주요 API는 인증 없이 호출할 수 없도록 한다.
- HTTPS 적용 여부는 서버 운영 정책에 따라 결정한다.

### 11.4 유지보수성

- 장비와 압축기를 프로그램 수정 없이 등록 및 변경할 수 있어야 한다.
- 채널 및 경보 기준값을 프로그램 수정 없이 변경할 수 있어야 한다.
- 로그를 통해 통신, 경보, 시스템 오류를 추적할 수 있어야 한다.
- 프로토콜 변경에 대응할 수 있도록 통신부와 프로토콜 해석부를 분리한다.
- 보고서와 일지 기능은 향후 항목 추가가 가능하도록 설계한다.
